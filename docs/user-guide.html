01 What is this, exactly?

Think of it as a fully-fitted workshop, not a pile of raw materials. Every time you start a new client website, you'd otherwise spend the first day or two wiring up the same things: forms, spam protection, email sending, page structure. This kit does all of that once, so every new project starts already-equipped.

🧰

A template, not a product

You don't edit this kit directly. Each new project makes its own copy, so changes to one client's site never touch another's.

📨

Comes with a working contact form

Visitors can message you, and it actually arrives in an inbox — spam-guarded, tested, ready to adapt.

🔑

Your keys stay yours

Passwords and API keys for a project live only on your computer, in one file that is never uploaded or shared.

02 What's inside the kit

You don't need to understand how each piece works — just what it's for. Here's the equipment list.

🖼️

Page building blocks

Buttons, cards, menus, pop-ups, image carousels, accordions — the common pieces most websites need, already styled and ready to arrange.

📬

Contact form + email

A working "get in touch" form that checks what visitors type and emails you the result, formatted nicely.

🛡️

Spam & bot protection

A hidden trap for automated bots, plus an optional "I'm not a robot" style check, so the form doesn't fill your inbox with junk.

🐢

Smooth scrolling & motion

Pages scroll and animate with a polished, modern feel out of the box.

🔍

Search-engine setup

Page titles, search-result descriptions, the sitemap Google reads, the breadcrumb trail on nested pages, and the preview card that appears when someone shares a link on WhatsApp or LinkedIn — all generated from one file, src/config/site.ts. Fill in your business address there and the site also tells Google where you are.

📈

Visitor analytics & speed tracking

Once deployed, you can see how many people are visiting and where they're coming from — plus how fast the site actually feels for real visitors. Google uses that speed as one ingredient in where it ranks you.

03 Before you start

Two things need to be on your computer before you scaffold your first project, and a few account keys are worth gathering in advance so the setup wizard doesn't leave you hunting for them mid-way through.

Install once, use for every project

ToolWhat it's forWhere to get it
Node.js requiredThe engine that runs the website on your computer while you work on it.nodejs.org — choose the LTS version
Git requiredKeeps track of every change you make, like unlimited "undo" for a whole project.git-scm.com

Accounts to have ready

You can start without these and add them later — the site will simply skip the related feature until you do. But it's faster to have them open in a tab.

  • Resend account & API key powers the contact form Free to start. Sign up at resend.com, then find your key under API Keys. It begins with re_.
  • Cloudflare Turnstile keys optional — bot check Free. Set up a "widget" at the Cloudflare dashboard to get a site key and a secret key.
  • Upstash Redis URL & token optional — limits spam submissions Free tier available at upstash.com. Without this, the form still works, it's just not rate-limited.
How to get your Upstash Redis URL & token (step by step)

Create an Upstash account

Go to upstash.com and sign up using GitHub, Google, or email — the free tier is enough for a rate-limited contact form.

Create a Redis database

Click Create Database, then fill in:

  • Database name: anything you'll recognise later, e.g. website-rate-limit.
  • Region: whichever is closest to where the site will be hosted. For Hostinger, Toronto or a nearby US region is usually a good pick if it's offered.

Click Create.

Find your Redis credentials

Open the database you just created and go to its Details (sometimes labelled the database overview). You'll see two values that go straight into .env.local:

.env.local values
UPSTASH_REDIS_REST_URL=https://xxxx-12345.upstash.io
UPSTASH_REDIS_REST_TOKEN=AXXXXXXXXXXXXXXXXXXXXXXXXX

For example, if the dashboard shows:

Example, as shown on the dashboard
Redis URL:
https://kind-dolphin-12345.upstash.io

Redis Token:
AXBCDEFGHIJKLMNOPQRSTUVWXYZ123456789

...then those are exactly the two values the setup script's Upstash prompts are asking for.

How to get your Cloudflare Turnstile keys (step by step)

Create a Cloudflare account

Go to dash.cloudflare.com/login and sign in, or create a free account. You do not need to host your website on Cloudflare to use Turnstile — it works as a standalone bot-check widget.

Open Turnstile in the dashboard

Once signed in, find Turnstile in the left-hand menu — or go straight to the Turnstile widget dashboard — then click Add widget (sometimes labelled Create widget).

🔗
Quick link straight to this Cloudflare account's Turnstile page

dash.cloudflare.com/…/turnstile — skips the menu hunting entirely. This one is tied to a specific Cloudflare account ID, so it only works while signed into that same account; if it ever 404s or redirects oddly, fall back to the general link above and navigate to Turnstile manually.

Configure the widget

Fill in a Widget name — anything you'll recognise later, e.g.:

Example widget name
Client Site Contact Form

Choose Managed mode (recommended — Cloudflare decides how much of a challenge to show). Under Domains, add every domain the form will run on, for example:

Domains to add
yourdomain.com
www.yourdomain.com
localhost
127.0.0.1

Adding localhost and 127.0.0.1 is what lets the widget work while you're testing on your own computer, before the site is live. Click Create.

Copy your keys

Cloudflare shows two values — these go straight into .env.local:

.env.local values
NEXT_PUBLIC_TURNSTILE_SITE_KEY=0x4AAAAAAAxxxxxxxxxxxxxxxx
TURNSTILE_SECRET_KEY=0x4AAAAAAAxxxxxxxxxxxxxxxx
⚠️
Copy the Secret key now — you won't get a second look

Cloudflare only displays the full secret key at the moment it's created. If you navigate away before copying it, you'll need to generate a new one. Paste both values into .env.local right away.

04 Starting a new project

This is the whole process, start to finish. One script does the cloning, installing, and configuring for you — you just answer its questions.

📍
Two different folders are involved — and PowerShell only ever knows about one of them

The tool's home: wherever you save new-project.ps1 itself (step 2). You set this up once and rarely think about it again. PowerShell does not care where this is.
Your workspace: the folder PowerShell is "standing in" the moment you press Enter to run the script (step 1). This — and only this — decides where the new project folder appears. The script has no memory of any other folder; nobody tells it about your workspace except you, by literally standing there first. See the worked example at the end of this section for a complete walk-through of this exact point.

Move into your workspace folder — every single time, before running the script

Decide on one folder where you'll keep all client sites — for example D:\Websites\Clients. Every project you scaffold will get its own subfolder inside it. This step is not a one-off setup task: you repeat it every time you start a new project, no matter where new-project.ps1 itself is saved.

Open PowerShell (search "PowerShell" in the Start menu), then move into your workspace folder with cd:

PowerShell — type this first, every time
cd "D:\Websites\Clients"

Or skip typing cd altogether: open the D:\Websites\Clients folder in File Explorer, click into its address bar, type powershell, and press Enter — a terminal opens already standing there.

✅
How to tell it worked

The PowerShell prompt itself shows the folder you're in, e.g. PS D:\Websites\Clients>. Before typing anything else, check that this matches the folder you meant — everything from here on happens relative to it, regardless of what you do next.

The very first time only: get the launcher script onto your computer

new-project.ps1 is the file that does all the work. It lives inside the template on GitHub, so before you can run it, you save your own copy onto your computer — just once, ever. After that, you reuse that same saved copy for every future project, no matter which client folder you're working in.

To keep this simple, both methods below save it to the exact same place: Documents\dev-tools\new-project.ps1. Pick one method — they produce an identical result, so there's nothing to gain from doing both.

Method A — type a command

Paste this into PowerShell and press Enter:

PowerShell — run once, ever, from anywhere
New-Item -ItemType Directory -Force -Path "$env:USERPROFILE\Documents\dev-tools" | Out-Null
Invoke-WebRequest -Uri "https://raw.githubusercontent.com/demre/nextjs-site-template/master/scripts/new-project.ps1" -OutFile "$env:USERPROFILE\Documents\dev-tools\new-project.ps1"

— OR —

Method B — download it by clicking, like any other file

Open this link in your browser and click the Download raw file button (top-right of the code). When the "Save As" box appears, browse to your Documents folder, create a new folder there named dev-tools, open it, and save the file inside — so it ends up at the same Documents\dev-tools\new-project.ps1 as Method A.

Used Method A already? Then Method B would just create a duplicate — no need to also do this. Whichever one you did, you're finished with this step.

Optional: I'd rather save it somewhere other than Documents

Totally fine — the script works identically no matter where it's saved. With Method A, replace both quoted paths in the command with your chosen folder. For example, to save it into D:\Websites instead:

PowerShell — same idea, different folder
New-Item -ItemType Directory -Force -Path "D:\Websites" | Out-Null
Invoke-WebRequest -Uri "https://raw.githubusercontent.com/demre/nextjs-site-template/master/scripts/new-project.ps1" -OutFile "D:\Websites\new-project.ps1"

With Method B, just browse to that folder instead of Documents in the "Save As" box — no command needed either way. Whatever you choose, that's the path you'll use in step 3 below instead of the Documents one.

Nothing runs yet. This step only places the file on your computer; it does not create a project or touch your workspace folder from step 1.

Every time you start a new project: run the script

Make sure you're still in the same PowerShell window from step 1 — the one standing inside your workspace folder. Now run the script by its full path. Pointing at its full path is enough to run it; doing so does not move PowerShell into the script's folder, and does not need to.

If you saved it to the default Documents location in step 2:

PowerShell — default location
& "$env:USERPROFILE\Documents\dev-tools\new-project.ps1"

Or, if you followed step 2's optional section and saved it to D:\Websites instead:

PowerShell — custom location, e.g. D:\Websites
& "D:\Websites\new-project.ps1"

Whichever one applies to you, the folder in this command is just wherever you saved new-project.ps1 in step 2 — swap it for your own path if it's neither of these two.

🔤
Why does the first command have $env:USERPROFILE and the second doesn't?

$env:USERPROFILE is a stand-in PowerShell automatically replaces with your personal Windows folder — something like C:\Users\YourName — which is different on every computer and every account. It's used there because "Documents" means a different full path depending on who's logged in. D:\Websites, on the other hand, is already a fixed, complete path that means the same thing on that machine no matter who's signed in, so there's nothing to fill in — you just write it as-is. Same rule either way: PowerShell needs the real, full path to the file; a variable like $env:USERPROFILE only appears when part of that path changes per person.

The & at the start tells PowerShell "run this file" — it's required whenever a script's path contains spaces or is wrapped in quotes, which most real-world paths are.

⚠️
There is nowhere you "tell" the script your workspace — cd in step 1 is the entire mechanism

This trips a lot of people up, so to be blunt: there is no setting, no config file, and no place in new-project.ps1 itself where a folder like D:\Websites\Clients is written down. The only thing connecting the script to that folder is you physically standing there — by running cd "D:\Websites\Clients" — in the same PowerShell window, immediately before running the script. That's it. Nothing else links them.

So if step 1 gets skipped, or you cd into the wrong folder, the script doesn't error out or guess — it just creates the new project in whatever folder PowerShell happened to be standing in at that moment, wherever that is. That could easily be the folder the script itself is saved in, if you opened PowerShell there instead. Always re-check the prompt (PS D:\Websites\Clients>) right before pressing Enter on step 3 — that path is where your new project is about to appear.

Answer the prompts

Type a project name, answer a few questions about the business, then paste in the keys you gathered in the step above. Press Enter to skip anything optional — you can always add it later.

Prompts you'll see
Project name (e.g. acme-marketing-site): acme-marketing-site
Site URL [http://localhost:3000]: (press Enter)
Site / business name (used in titles, share previews and search results): Acme Joinery
One-sentence description of the business (shown in search results): Bespoke fitted kitchens in Leeds.
Business phone number (optional): (press Enter)
Resend API key: re_xxxxxxxxxxxx
Contact form 'send to' email address: hello@acme.com
💡
The name and description are what the public sees

They become the browser tab title, the grey summary line under your site in Google's results, and the preview card when someone shares a link on WhatsApp or LinkedIn. Write the description as a sentence a customer would read — roughly 15 to 25 words. Both are easy to change later in src/config/site.ts.

📌
Where does the new project folder go?

Right here, inside whatever folder PowerShell was standing in during step 1 — not inside the folder where new-project.ps1 itself lives. The name you type at this prompt becomes the new subfolder's name. See the worked example below for a complete walk-through.

Let it finish

The script downloads the template, installs everything the site needs, writes your keys into a private settings file, and puts the business name and description into src/config/site.ts. This takes a minute or two — you'll see download progress scroll by.

💡
That's normal

Long lists of package names and the odd yellow "deprecated" warning are ordinary noise from the install process, not errors.

Your site opens automatically

The script finishes by starting the site on your computer. Open a browser and go to:

Browser
http://localhost:3000

This is a private preview — only visible on your computer, not on the internet yet. Try the /contact page to see the working contact form.

Just before the site starts you'll see a short yellow note asking you to finish filling in the business details. That's the next step below — it isn't an error.

Fill in the rest of the business details

Open src/config/site.ts in the project folder. Whatever you typed at the prompts is already in place; the business block below is not. Complete it with the real address, opening hours, and links to any social profiles.

If you skipped the description prompt, the script will have printed a warning — that one does need filling in before the site goes live, because the placeholder text would otherwise show up under your site's name in Google.

📍
The address is the one that really matters

With a street address filled in, the site quietly tells Google it's a real business at a real place — the information behind map results and the business panel that appears beside search results. Leave it blank and the site still works perfectly and is still indexed; it just describes itself as a generic organisation instead. Nothing breaks either way, so it's safe to come back to this once the client sends their details.

🧭 Worked example — where everything actually ends up

Say you saved the launcher script to the default location in step 2 (Documents\dev-tools\new-project.ps1, which lives on your C: drive), your workspace folder is D:\Websites\Clients on a completely different drive (step 1), and at the prompt (step 4) you type the project name acme-marketing-site. Notice these two locations don't even share a drive letter — and that's exactly the point: they don't need any relationship at all. Here's exactly what you'd type, in order:

06 Three rules worth memorising

🔒
Never share or upload .env.local

It holds real, working keys. If it ever ends up in an email, chat message, or on GitHub, treat every key inside it as compromised — regenerate them straight away from the original service (Resend, Cloudflare, Upstash).

🧾
Each project keeps its own copy of the kit

Editing one client's website never changes the shared template, and updates to the template don't automatically reach projects you've already started.

✉️
The free Resend tier only emails your own address, at first

Until you verify a domain on resend.com/domains, test emails can only be sent to the address you signed up with. This is a Resend safety limit, not a bug in your site.

07 Taking a site from your computer to the internet

This kit is built to deploy on Vercel, the company behind the underlying technology (Next.js). It's a short, mostly point-and-click process.

  • Push the project to its own GitHub repositorySeparate from the template — one repository per client site.
  • Connect that repository to VercelVercel builds and hosts the site automatically whenever you push a change.
  • Re-enter your keys in Vercel's dashboardUnder Project Settings → Environment Variables — copy the same names and values from your local .env.local. This step exists because .env.local intentionally never leaves your computer.
  • Point your domain at VercelAdd your domain in Vercel's dashboard and update its DNS records as instructed. If you use both www.yoursite.com and yoursite.com, set one as the primary and let Vercel redirect the other — otherwise search engines treat them as two competing copies of the same site.
  • Set NEXT_PUBLIC_SITE_URL to the real domainIn Vercel's Environment Variables, change it from http://localhost:3000 to your live address, e.g. https://yoursite.com. Every link Google reads — the sitemap, the "official address" of each page, the image on shared link previews — is built from this value. Leave it pointing at localhost and search engines get a site full of dead links. The build will refuse to run if it's missing entirely.
  • Once live, submit the site to GoogleCreate a free Google Search Console account, verify the domain, and submit https://yoursite.com/sitemap.xml. This is what gets the site indexed in days rather than weeks. The easiest way to verify: choose the "HTML tag" method, copy the content="..." value it gives you, and paste it into NEXT_PUBLIC_GOOGLE_SITE_VERIFICATION in Vercel's Environment Variables — no file upload or DNS change needed.

08 Common questions

The setup script finished, but the site didn't open in my browser
Open one yourself and go to http://localhost:3000. As long as the PowerShell window still shows the server running ("Ready" in green), the site is live locally.
I submitted the contact form and nothing arrived
Check three things in order: (1) is RESEND_API_KEY filled in inside .env.local? (2) is the "send to" address the same one you signed up to Resend with — see the golden rule above? (3) check your spam folder.
Do I need the Turnstile or Upstash keys to get started?
No. Both are optional. Leave their prompts blank and the site runs fine — it simply skips the bot-check widget and the spam rate-limit until you add them.
Can I run two projects at the same time?
Yes, but only one can use localhost:3000 at once. Stop the first with Ctrl+C in its PowerShell window before starting the next, or the second project will automatically pick the next free port (3001, 3002…).
I accidentally closed the PowerShell window — did I lose my work?
No. Your files are saved on disk exactly as they were. Just open PowerShell again, move into the project folder with cd project-name, and run npm run dev to keep working.
How do I change the page title or the description Google shows?
Open src/config/site.ts and edit name and description near the top. They flow through to the browser tab, search results, and link previews everywhere on the site — you don't need to edit each page.
I added a new page. Does anything else need updating?
Yes — one line. Add it to the routes list at the bottom of src/config/site.ts, otherwise search engines won't be told the page exists. Nothing will appear broken if you forget, which is exactly why it's worth remembering.
When I share the link, the preview shows the wrong name — or no image
Two likely causes. First, check NEXT_PUBLIC_SITE_URL in Vercel points at the real domain, not localhost. Second, WhatsApp, LinkedIn and Facebook cache previews for days — they may still be showing an old copy. Paste the link into Facebook's Sharing Debugger or LinkedIn's Post Inspector and ask it to re-fetch.
The site has been live for a week and still isn't on Google
That's normal — new sites take days to weeks. To speed it up, verify the domain in Google Search Console and submit https://yoursite.com/sitemap.xml. While you're there, "URL Inspection" will tell you exactly what Google has seen so far.
Do I need to make a logo or share image?
Not to launch. The browser icon and the link-preview image are drawn automatically from the business name. They're deliberately plain, so replacing them with real artwork is a sensible early improvement — but nothing is missing or broken until you do.

09 Glossary — jargon, decoded

TermIn plain words
API keyA long password that lets one piece of software (your site) talk to another (like Resend) on your behalf.
Repository / repoA project's complete folder of files, plus its full history of changes, stored on GitHub.
TemplateA starting-point repository other projects are copied from — this kit.
DeployPublishing your site so it's reachable on the internet, not just on your computer.
localhostA private address meaning "this computer" — only you can see pages served there.
HoneypotA form field hidden from real visitors but visible to simple bots, which fill it in and unknowingly reveal themselves.
Environment variableA named setting (like a key or address) the site reads at start-up, kept outside the code itself.
SEOSearch engine optimisation — the work of making a site easy for Google to understand and rank. This kit handles the technical groundwork; the words on your pages do the rest.
SitemapA machine-readable list of every page on the site, handed to search engines so nothing gets missed. Yours lives at /sitemap.xml and builds itself.
robots.txtA short note to search engines saying which parts of the site they're welcome to look at.
Meta descriptionThe grey summary line under your site's name in Google's results. Comes from description in src/config/site.ts.
Open Graph / OG imageThe picture-and-title card that appears when a link to your site is shared on WhatsApp, LinkedIn, Slack or Facebook.
Canonical URLThe one official address for a page. It stops search engines treating www.yoursite.com and yoursite.com as two rival copies competing with each other.
Structured dataBusiness facts — address, phone, opening hours, breadcrumb trail — written in a format Google reads directly, rather than having to guess at from the page text.
BreadcrumbsThe "Home / Contact" trail near the top of a nested page, both as something visitors can click and as structured data telling Google how the page fits into the rest of the site.
Google Search ConsoleA free Google tool showing what your site looks like from Google's side: which pages are indexed, which searches bring people in, and what's going wrong. Verify ownership with the "HTML tag" method and NEXT_PUBLIC_GOOGLE_SITE_VERIFICATION.
FaviconThe tiny icon in the browser tab and in bookmarks.
